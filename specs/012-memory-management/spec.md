# 记忆管理（Memory Management）能力规范

## 概述

记忆管理模块为 AgentX 系统提供长期记忆存储、检索、去重和重要性加权功能。该模块通过自动抽取对话中的有价值信息，结合向量相似度检索和重要性评分机制，实现对用户的偏好、目标、事实和情景信息的智能化管理，显著提升多轮对话的连贯性和个性化体验。

## 核心能力

### 1. 长期记忆存储

**功能描述**：将用户对话中的关键信息自动抽取并持久化存储，支持跨会话的长期记忆保持。

**核心特性**：
- 自动提取：从对话内容中智能识别并提取有价值的记忆点
- 类型分类：将记忆按照性质分为四种类型（PROFILE/TASK/FACT/EPISODIC）
- 重要性评分：为每条记忆分配 0.0-1.0 的分数，用于写入阈值和读取加权
- 标签体系：支持记忆标签的添加和管理，便于筛选和分类
- 元数据存储：提供灵活的数据字段（JSONB），支持结构化负载

### 2. 记忆检索

**功能描述**：基于查询内容的语义相似度和记忆重要性，智能召回最相关的记忆条目。

**核心特性**：
- 向量相似度检索：使用 PGVector 作为向量数据库，通过 SQLAlchemy 进行 ORM 映射，支持高效的余弦相似度匹配
- 嵌入模型集成：兼容 OpenAI Embeddings API 和本地 Sentence Transformers，支持用户专属配置动态切换
- 重要性加权：综合计算相似度分值和重要性分值，提升检索质量（默认权重：相似度 70%，重要性 30%）
- 多租户隔离：严格按 user_id 级别隔离记忆数据和检索范围，向量存储元数据中包含用户过滤条件
- 自定义 Top-K：支持灵活调整召回条目数量（推荐值：Top-16 用于初筛，最终输出 Top-5）
- 状态过滤：仅返回 status=active 的记忆记录，自动过滤已归档数据
- 索引优化：支持 ivfflat 和 HNSW 两种索引策略，ivfflat 适用于万级以下数据（召回率>95%），HNSW 适用于大规模场景（召回率>98%）

### 3. 去重/合并

**功能描述**：通过语义哈希机制实现记忆的去重和智能合并，避免重复信息积累。

**核心特性**：
- 语义去重：对记忆文本进行标准化处理，生成 SHA-256 哈希值
- 幂等写入：对相同内容的记忆进行合并而非重复创建
- 智能合并策略：
  - 重要性取最大值
  - 标签合并去重
  - 文本选用更丰富版本
  - 数据字段智能合并

### 4. 记忆管理

**功能描述**：提供记忆条目的增删查改管理界面，支持用户对个人记忆的完整控制。

**核心特性**：
- 分页查询：支持按类型、标签、时间范围分页浏览记忆列表（默认页大小 20，最大 100）
- 手动创建：允许用户手动添加记忆条目，支持重要性评分和标签自定义
- 编辑更新：支持用户修改记忆文本、调整重要性评分、增删标签
- 归档删除：支持记忆的软删除（status 置为 archived），保留数据可恢复
- 物理删除：支持 GDPR"被遗忘权"要求的彻底物理删除（需二次确认）
- 类型过滤：支持按记忆类型筛选显示，支持多类型组合过滤
- 批量操作：支持批量归档、批量导出、批量标签管理

## 记忆类型

### PROFILE（用户偏好）

**定义**：用户稳定的偏好、人格特质或固定的格式要求。

**示例**：
- "以后都用简体中文回答"
- "回答尽量附带 bash 示例"
- "输出格式要求 JSON"

**适用场景**：
- 用户明确表达的交互偏好
- 固定的输出格式要求
- 持续性的语言或风格偏好

### TASK（目标任务）

**定义**：明确的中长期目标或持续性计划。

**示例**：
- "一周内完成 Agent 项目并补齐文档"
- "这个月学习 Python 基础"
- "目前正在重构旧系统的用户模块"

**适用场景**：
- 用户陈述的中长期目标
- 正在进行的持续任务
- 有明确时间框架的计划

### FACT（稳定事实）

**定义**：与用户身份或工作环境相关的、在较长时间内稳定不变的事实。

**示例**：
- "主要编程语言是 Python"
- "平时在上海办公"
- "公司名称是 X Tech"

**适用场景**：
- 用户的基本信息
- 工作环境相关事实
- 技能栈背景信息

### EPISODIC（情景信息）

**定义**：未来 3-5 轮交互内明显有帮助的情节性信息。

**示例**：
- "刚才我们讨论了 Kafka 消息队列的配置"
- "上一步配置了 API 密钥"
- "之前提到了 Spring Boot 的版本"

**适用场景**：
- 短期内的上下文关联
- 跨轮次的信息引用
- 临时但有价值的情节

## 技术选型与约束

### 向量数据库

**主选方案：PGVector**
- 理由：与现有 PostgreSQL 数据库无缝集成，无需额外部署，降低运维成本
- 版本要求：PostgreSQL 14+，pgvector 扩展 0.5+
- 性能基准：单用户<1000 条记忆时，Top-16 检索延迟<300ms；万级数据时<800ms
- Python 客户端：SQLAlchemy 2.0+ ORM + psycopg2 驱动

**备选方案：Chroma**
- 适用场景：需要独立向量数据库、追求更高性能的场景
- 优势：原生向量索引、支持 HNSW、分布式扩展能力强
- Python 客户端：chromadb 官方库 0.4+

### 嵌入模型

**云服务：OpenAI Embeddings**
- 模型：text-embedding-3-small（性价比高）、text-embedding-3-large（高精度）
- 维度：1536 维
- 延迟：<500ms/条（批量处理可优化）

**本地部署：Sentence Transformers**
- 模型：all-MiniLM-L6-v2（快速）、bge-large-zh（中文优化）
- 维度：384 维或 1024 维
- 延迟：<100ms/条（CPU 即可）

### 重要性评分机制

**LLM 调用方式（主选）**
- 通过结构化的 System Prompt 指导 LLM 进行重要性评估
- 评分维度：信息稳定性、复用频率、个性化程度、时间敏感性
- 评分范围：0.0-1.0，保留两位小数
- 阈值策略：PROFILE/TASK/FACT≥0.8 入库，EPISODIC≥0.9 入库
- 成本控制：单次抽取最多输出 3 条记忆，避免 Token 爆炸

**规则方式（备选）**
- 基于关键词匹配和文本长度规则
- 适用场景：LLM 服务不可用时的降级策略

### 容量管理与降级策略

**建议容量**
- 单用户活跃记忆：建议<1000 条（性能最优区间）
- 记忆文本长度：上限 5000 字符（超出截断）
- 标签数量：单条记忆<10 个标签
- 数据字段：JSONB 负载<10KB

**超限处理策略**
- 自动归档：当用户记忆数>1200 条时，自动归档最早且重要性<0.6 的记忆
- 分级存储：高重要性（≥0.8）常驻内存，低重要性（<0.6）冷存储
- 用户通知：当记忆数接近上限时，提醒用户手动清理或开启自动归档
- 降级模式：极端情况下（>2000 条），暂停 EPISODIC 类型自动抽取，仅保留 PROFILE/FACT

### 隐私识别与过滤

**混合识别策略**
- 规则引擎：正则表达式识别身份证号、银行卡号、手机号、邮箱等结构化敏感信息
- LLM 识别：通过 Prompt 指导模型识别地址、姓名、公司名等非结构化隐私
- 双重过滤：抽取前初步筛查 + 抽取后精细审核

**隐私数据处理**
- 匿名化：精确地址替换为城市级（如"上海市浦东新区"→"上海"）
- 脱敏：手机号中间四位替换为*号
- 拒绝抽取：密钥、密码、Token 等直接丢弃不入库

### 记忆注入时机与冲突处理

**注入时机**
- 每次对话触发：在对话开始时自动检索 Top-5 相关记忆注入上下文
- 阈值触发：当用户消息与某条记忆相似度>0.85 时，主动提示"您之前提到过..."
- 定时触发：每隔 5 轮对话，重新检索并刷新记忆上下文

**冲突处理**
- 时间优先：当记忆与当前上下文矛盾时，以最新信息为准
- 重要性优先：当记忆重要性≥0.9 时，向用户确认是否更新旧记忆
- 显式更新：用户明确表示"我之前说的 XX 不对"时，自动归档旧记忆并创建新记忆

### 场景一：个性化对话体验

**描述**：用户在使用 Agent 进行多轮对话时，系统能够记住用户的偏好和上下文，提供个性化的响应。

**用户工作流**：
1. 用户首次表达偏好："以后都用中文回答，尽量详细一些"
2. 系统自动提取并保存为 PROFILE 类型记忆
3. 后续对话中，系统自动召回该偏好记忆
4. 系统在生成回复时，自动应用该偏好设置

**价值体现**：
- 提升用户体验的连贯性
- 减少重复说明的次数
- 增强个性化服务能力

### 场景二：任务进度跟踪

**描述**：用户在多轮对话中描述自己的目标和进展，系统能够记住这些信息并适时提供协助。

**用户工作流**：
1. 用户说明目标："本周要完成 Agent 项目搭建"
2. 系统提取为 TASK 类型记忆
3. 用户在不同会话中继续讨论相关任务
4. 系统自动提供与该任务相关的建议和帮助

**价值体现**：
- 支持长期任务的连续性
- 提供上下文相关的智能建议
- 增强系统的主动服务能力

### 场景三：背景信息利用

**描述**：用户分享自己的背景信息，系统能够记住这些事实并在适当的场景中利用。

**用户工作流**：
1. 用户提及： "我是做 Java 开发的，主要使用 Spring 框架"
2. 系统提取为 FACT 类型记忆
3. 用户后续询问技术问题时，系统优先推荐 Java/Spring 相关方案
4. 系统基于用户的技术栈提供更有针对性的建议

**价值体现**：
- 提高建议的针对性
- 增强技术支持的个性化
- 优化问题解答的效率

### 场景四：跨会话的上下文保持

**描述**：用户在不同会话之间进行知识讨论，系统能够记住之前讨论的重点。

**用户工作流**：
1. 用户讨论了分布式系统的 CAP 理论
2. 系统提取 EPISODIC 类型记忆
3. 用户开始新的会话，继续讨论一致性算法
4. 系统自动回忆起之前讨论的 CAP 理论背景
5. 系统结合上下文提供更连贯的解释

**价值体现**：
- 保持知识学习的连续性
- 支持深度技术讨论
- 增强理解的连贯性

## 不抽取的场景

为保证记忆质量，系统明确不提取以下类型的信息：

### 一次性操作/命令

- 示例："调用子 agent 查看 user 目录下的文件"
- 示例："运行脚本 X", "ls/cd/cat/npm/pip/install"
- 原因：这些操作对后续对话没有复用价值

### 临时数据或结论

- 示例：仅与当轮问题相关的临时细节
- 原因：后续复用价值不明确，会污染记忆空间

### 隐私或敏感信息

- 示例：身份证号、银行卡、精确住址、电话号码
- 示例：密钥、token、密码
- 原因：涉及用户隐私和安全风险

## 使用场景

### 自动抽取

- **触发时机**：每轮对话结束后自动触发
- **抽取源**：基于用户当轮发言内容
- **评估机制**：通过 LLM 进行价值判断和重要性评分
- **阈值策略**：仅保留 importance ≥ 0.8 的记忆（EPISODIC 类型更严格，需 ≥ 0.9）

### 异步处理

- **处理方式**：使用异步任务执行器（memoryTaskExecutor）
- **性能优化**：不影响主对话流程的响应速度
- **错误处理**：抽取失败不影响正常对话

### 向量化存储

- **嵌入模型**：使用用户专属的嵌入配置
- **元数据关联**：向量中包含 user_id、item_id、type、tags、status 等信息
- **检索效率**：支持高效的语义相似度检索

### 用户隔离

- **数据隔离**：每个用户的记忆完全隔离
- **检索隔离**：检索时仅召回本用户的记忆
- **权限控制**：通过 user_id 实现严格的多租户隔离

## 数据模型

### 记忆条目（MemoryItem）

**核心字段**：
- `id`：记忆条目唯一标识（UUID）
- `user_id`：归属用户ID
- `type`：记忆类型（PROFILE/TASK/FACT/EPISODIC）
- `text`：记忆文本内容
- `data`：结构化数据（JSONB）
- `importance`：重要性评分（0.0-1.0）
- `tags`：标签列表
- `source_session_id`：来源会话ID
- `dedupe_hash`：去重哈希值
- `status`：状态（1=active, 0=archived）

### 候选记忆（CandidateMemory）

**用途**：记忆抽取器的输出结构
- `type`：记忆类型
- `text`：记忆文本
- `importance`：重要性评分
- `tags`：标签列表
- `data`：结构化数据

### 检索结果（MemoryResult）

**用途**：记忆检索的返回结构
- `itemId`：记忆条目ID
- `type`：记忆类型
- `text`：记忆文本
- `importance`：重要性评分
- `tags`：标签列表
- `score`：综合评分（相似度与重要性的加权和）


## 安全、隐私与合规

### 数据隔离

- 严格的多租户隔离机制，通过 user_id 强制过滤
- 检索时的用户级过滤，WHERE 条件必须包含 user_id
- 禁止跨用户数据访问，应用层 + 数据库层双重校验
- 向量存储元数据中包含 user_id，确保检索隔离

### 隐私保护

- 隐私信息识别与过滤（规则引擎 + LLM 双重机制）
- 敏感信息不抽取（密钥、密码、Token 直接丢弃）
- 支持记忆的归档删除（软删除，保留恢复能力）
- 支持 GDPR"被遗忘权"（彻底物理删除，需二次确认）
- 匿名化处理：精确地址→城市级，手机号脱敏

### 审计与合规

- 记忆来源会话追踪（source_session_id 字段）
- 创建和更新时间记录（created_at、updated_at 字段）
- 操作日志记录：谁、何时、做了什么操作（可扩展到独立审计表）
- 数据导出支持：用户可申请导出个人全部记忆数据（JSON 格式）
- 删除策略：软删除默认保留 30 天，超期自动物理清理

### 安全加固

- HTTPS 传输加密：所有 API 请求强制 HTTPS
- 敏感字段加密：data 字段可选 AES-256 加密存储
- 访问控制：基于 JWT 的用户鉴权，细粒度到单条记忆
- 速率限制：单用户每秒最多 10 次记忆相关 API 请求
- SQL 注入防护：使用 ORM 参数化查询，禁止字符串拼接

## 功能特性

### 自动抽取

- **触发时机**：每轮对话结束后自动触发（异步处理，不影响主对话响应）
- **抽取源**：基于用户当轮发言内容 + 最近 3 轮对话历史（增强上下文理解）
- **评估机制**：通过 LLM 进行价值判断和重要性评分（调用用户配置的 ChatModel）
- **阈值策略**：仅保留 importance ≥ 0.8 的记忆（EPISODIC 类型更严格，需 ≥ 0.9）
- **版本控制**：抽取 Prompt 模板支持版本管理，便于迭代优化（当前版本：v1.0）
- **失败重试**：抽取失败自动重试 2 次（指数退避策略：1s、2s 间隔）
- **频率限制**：单用户每分钟最多触发 5 次抽取，防止 Token 消耗过快

### 异步处理

- **处理方式**：使用 asyncio 异步任务执行器（memoryTaskExecutor）
- **并发控制**：最大并行嵌入数限制为 3，避免网络拥塞
- **性能优化**：不影响主对话流程的响应速度，后台静默处理
- **错误处理**：抽取失败不影响正常对话，记录错误日志并告警
- **任务队列**：使用 Redis 作为任务队列缓冲，支持削峰填谷

### 向量化存储

- **嵌入模型**：使用用户专属的嵌入配置（支持 OpenAI/Sentence Transformers）
- **元数据关联**：向量中包含 user_id、item_id、type、tags、status 等信息
- **检索效率**：支持高效的语义相似度检索（ivfflat 索引，lists=100）
- **批量优化**：支持批量向量化（batch_size=10），减少 API 调用次数
- **索引重建**：每月自动重建一次向量索引，优化检索性能

### 用户隔离

- **数据隔离**：每个用户的记忆完全隔离，通过 user_id 严格区分
- **检索隔离**：检索时 WHERE 条件强制包含 user_id 过滤
- **权限控制**：通过 user_id 实现严格的多租户隔离，禁止越权访问
- **审计日志**：所有记忆操作记录审计日志（创建人、操作时间、IP 地址）

### 可扩展性机制

- **类型注册**：支持动态注册新的记忆类型（扩展 MemoryType 枚举）
- **元数据扩展**：data 字段采用 JSONB 格式，支持灵活的结构化数据扩展
- **插件化抽取器**：支持自定义抽取策略插件（实现 MemoryExtractor 接口）
- **向量存储抽象**：定义统一的 VectorStore 接口，支持多种后端切换

## 性能指标与基准

### 存储性能（单用户<1000 条记忆的基准）

- 抽取响应时间：< 5 秒（异步处理，含 LLM 调用）
- 向量化入库时间：< 2 秒/单条记忆（OpenAI API）；<200ms/条（本地模型）
- 去重查询时间：< 100ms（数据库索引命中）
- 批量保存时间：< 5 秒/10 条记忆（含向量化）

### 检索性能（单用户<1000 条记忆的基准）

- 相似度检索延迟：< 300ms（Top 16，ivfflat 索引）
- 加权排序时间：< 50ms（内存计算）
- 状态过滤时间：< 50ms（数据库层面过滤）
- 端到端检索耗时：< 500ms（从请求到响应）

### 容量指标与建议

- 单用户活跃记忆数：建议<1000 条（性能最优），上限 2000 条
- 记忆文本最大长度：5000 字符（超出自动截断并提示）
- 标签数量限制：单条记忆<10 个标签
- 数据字段大小限制：< 10KB（JSONB 格式）
- 向量数据库总容量：单实例支持千万级向量（PGVector 基准）

### 性能退化阈值

- 检索延迟警告：当 Top-16 平均延迟>800ms 时触发优化建议
- 容量警告：当用户记忆数>1200 条时提醒归档
- 索引重建建议：当数据量增长>50% 时建议重建索引
